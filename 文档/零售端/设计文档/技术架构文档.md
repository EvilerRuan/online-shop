# 零售商城 — 技术架构文档

## 1. 项目概述

在现有批发商城系统（Monorepo，pnpm workspaces）基础上扩展 B2C 零售商城。系统与批发端共享数据库、API 层和部分管理功能，通过渠道标识（channel）区分业务。

**新增模块：**
- `retail/` — 零售用户端（Taro 4.x + Vue 3 + NutUI 4.x + Pinia，支持 H5 + 微信小程序）
- `admin/` — 管理后台扩展零售管理模块（在现有 React 18 + Ant Design 5 基础上）
- `api/` — API 扩展零售端路由和管理后台零售路由
- `shared/` — 共享类型和常量扩展
- `supabase/migrations/` — 新增数据库迁移脚本（009-016）

## 2. 技术选型

| Vue 3 | 3.4+ | UI 框架 | 与 Taro 4.x 深度集成、Composition API |
| NutUI | 4.x | 移动端 UI 库 | Taro 官方推荐、京东出品、组件丰富 |

| 服务 | 用途 |
|------|------|

| Supabase Auth | 用户认证（扩展微信登录） |

### 2.5 选型原则

- **零售端选 Taro + Vue 3 + NutUI**：Taro 是目前最成熟的跨端框架，NutUI 与 Taro 深度集成，一套代码同时输出 H5 和微信小程序
- **管理后台扩展 React + Ant Design**：在现有后台基础上扩展，复用已有组件和模式
- **API 复用 Hono on Workers**：共享现有基础设施，通过路由前缀区分零售/管理路由
- **统一 TypeScript**：前后端全部使用 TypeScript，shared 包共享类型定义

### 3.2 请求流程

**零售端请求流程：**
1. Retail 应用发起 HTTP 请求到 Cloudflare Workers
2. Workers 中间件验证 JWT Token（retailAuthMiddleware）
3. 校验用户 channel 为 retail
4. 业务逻辑处理（运费计算、订单创建、积分操作等）
5. Workers 通过 Service Role Key 操作 Supabase Database
6. 返回统一格式响应

**微信登录流程：**
1. 小程序调用 `wx.login()` 获取临时 code
2. 发送 `POST /api/auth/wx-login` 携带 code
3. Workers 调用微信接口 `code2session` 获取 openid/unionid
4. 通过 openid 查找 profiles 表
5. 存在 → 生成 JWT 返回；不存在 → 创建用户 + profiles 记录 + 赠送积分 → 返回 JWT

**验证码登录流程：**
1. 用户输入手机号 → `POST /api/auth/send-code`（模拟，固定 123456）
2. 用户输入验证码 → `POST /api/auth/sms-login`
3. 校验验证码 → 查找/创建用户 → 返回 JWT

### 3.3 零售端与批发端关键差异

| 特性 | 批发端 | 零售端 |
|------|--------|--------|
| 前端框架 | Vue 3 + Vant 4 | Taro 4.x + Vue 3 + NutUI 4.x |
| 平台 | H5 / WebView | H5 + 微信小程序 |
| 登录方式 | 手机号+密码 | 微信登录 + 手机号+验证码 |
| 最小购买量 | min_order_qty（SKU 级别） | 1 件 |
| 价格 | price（SKU 级别） | retail_price（商品级别） |
| 运费 | 无 | 按收货城市计算 |
| 支付 | 待付款 → 管理员确认 | 下单即支付成功 |
| 售后 | 无 | 仅退款 / 退货退款 |
| 积分 | 无 | 注册/推荐/确认收货赠送 |
| 客服 | 无 | HTTP 消息 + 可选 WebSocket |

### 5.2 零售端 — 状态管理（Pinia）

```
stores/
├── useAuthStore.ts        # 认证状态（token, user, wxLogin, smsLogin, logout）
├── useCartStore.ts        # 购物车状态（items, totalPrice, selectedIds, 本地存储）
├── usePointsStore.ts      # 积分状态（balance, config 缓存）
└── useChatStore.ts        # 聊天状态（WebSocket 连接, messages, isPolling）
```

**useAuthStore 关键方法：**
- `wxLogin()` — 微信小程序登录（仅 weapp 环境）
- `smsLogin(phone, code)` — 验证码登录
- `sendCode(phone)` — 发送验证码
- `logout()` — 退出登录
- `checkToken()` — 启动时检查 Token 有效性

**useCartStore 关键特性：**
- 购物车数据存储在本地（localStorage），不依赖后端 API
- 与批发端的后端购物车 API 不同，零售端购物车纯前端管理
- 支持跨端持久化（Taro.setStorageSync）

### 5.3 零售端 — 登录态管理

```
应用启动
  │
  ├── 检查本地 Token 是否存在（Taro.getStorageSync）
  │     │
  │     ├── 存在 → 验证 Token 有效性
  │     │     │
  │     │     ├── 有效 → 进入首页
  │     │     │
  │     │     └── 无效 → 清除 Token → 跳转登录页
  │     │
  │     └── 不存在 → 跳转登录页
  │
  ├── 路由拦截
  │     │
  │     ├── 登录页 → 已登录则重定向首页
  │     │
  │     └── 其他页 → 未登录则跳转登录页
  │
  └── API 请求拦截器
        │
        ├── 自动附加 Authorization: Bearer <token>
        │
        └── 401 响应 → 清除 Token → 跳转登录页
```

### 6.2 中间件设计

**retailAuthMiddleware（零售认证中间件）：**
1. 从 Header 提取 `Authorization: Bearer <token>`
2. 验证 JWT Token（自签发，非 Supabase Auth）
3. 验证成功 → 将 user 信息（id, channel=retail）注入 context
4. 验证失败 → 返回 `{ code: 401, message: "未登录" }`

**与批发端 authMiddleware 的区别：**
- 批发端使用 Supabase Auth Token
- 零售端使用自签发 JWT（微信登录和验证码登录后签发）
- retailAuthMiddleware 额外校验 channel === 'retail'

### 6.3 关键业务逻辑 — 积分操作（RPC）

```
积分增加（add_points）：
│
├── 1. 开启事务
│     │
│     ├── 2. SELECT ... FROM profiles WHERE id = ? FOR UPDATE（行锁）
│     │
│     ├── 3. UPDATE profiles SET points_balance = points_balance + amount
│     │
│     ├── 4. INSERT INTO points_ledger（type=earn, reason, amount, balance_after）
│     │
│     └── 5. 提交事务
│
积分消耗（spend_points）：
│
├── 1. 开启事务
│     │
│     ├── 2. SELECT ... FROM profiles WHERE id = ? FOR UPDATE（行锁）
│     │
│     ├── 3. 校验 points_balance >= amount
│     │     │
│     │     ├── 充足 → 继续
│     │     │
│     │     └── 不足 → 回滚，返回 "积分不足"
│     │
│     ├── 4. UPDATE profiles SET points_balance = points_balance - amount
│     │
│     ├── 5. INSERT INTO points_ledger（type=spend, reason, amount, balance_after）
│     │
│     └── 6. 提交事务
```

### 6.4 关键业务逻辑 — 零售订单创建

```
POST /api/retail/orders
│
├── 1. 验证请求参数（地址信息、商品列表、备注）
│
├── 2. 计算运费
│     │
│     ├── 精确匹配省+市 → 命中则使用该配置
│     ├── 匹配省+city='' → 命中则使用该配置
│     └── 均未命中 → 使用默认运费
│     │
│     ├── fee_type=free → 运费为 0
│     ├── fee_type=free_threshold 且订单金额≥阈值 → 运费为 0
│     └── fee_type=fixed 或不满足免运费条件 → 使用 base_fee
│
├── 3. 开启数据库事务
│     │
│     ├── 4. 查询所有商品库存
│     │     │
│     │     ├── 库存充足 → 继续
│     │     │
│     │     └── 库存不足 → 回滚，返回 "xxx商品库存不足"
│     │
│     ├── 5. 扣减库存
│     │
│     ├── 6. 创建订单记录（channel=retail, shipping_fee, status=pending_shipment）
│     │
│     ├── 7. 创建订单商品记录（快照数据）
│     │
│     ├── 8. 更新商品销量
│     │
│     └── 9. 清空购物车中已结算商品
│
└── 10. 提交事务 → 返回订单信息
```

### 6.5 关键业务逻辑 — 售后状态流转

```
仅退款（refund）：
  pending → approved（管理员同意）→ completed（退款完成）
  pending → rejected（管理员拒绝）

退货退款（return_refund）：
  pending → processing（管理员同意退货）
  processing → processing（用户填写退货快递单号）
  processing → completed（管理员确认收货，退款完成）
  processing → rejected（管理员拒绝）
```

## 9. 运费计算方案

```
运费计算三级匹配：

输入：province（省）、city（市）、order_amount（订单金额）

1. 精确匹配：
   SELECT * FROM shipping_fees
   WHERE province = ? AND city = ? AND is_active = true
   → 命中 → 使用该配置

2. 省级匹配：
   SELECT * FROM shipping_fees
   WHERE province = ? AND city = '' AND is_active = true
   → 命中 → 使用该配置

3. 默认运费：
   SELECT value FROM system_settings
   WHERE key = 'default_shipping_fee'
   → 使用默认值

运费类型处理：
- fee_type = 'free' → 运费 = 0
- fee_type = 'fixed' → 运费 = base_fee
- fee_type = 'free_threshold' → 订单金额 >= free_threshold ? 0 : base_fee
```

## 14. 安全策略

| 安全项 | 实现方式 |
|--------|---------|
| 接口认证 | 零售端自签发 JWT + 中间件验证 |
| 管理权限 | 复用现有 adminMiddleware |
| 数据隔离 | RLS 策略 + API 层 user_id 校验 + channel 过滤 |
| 微信登录 | 服务端 code2session，不暴露 secret |
| 积分安全 | RPC 函数 + FOR UPDATE 行锁，防并发 |
| 文件上传 | 复用现有方案（类型白名单 + 大小限制） |
| XSS 防护 | 富文本内容过滤 |
| CORS | Workers 层配置允许域名 |
